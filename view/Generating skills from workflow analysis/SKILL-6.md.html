Skill 6: master-summary

name: master-summary description: Produce Brett's 📌 MASTER SUMMARY documents — the canonical record of a project or long working session that separates decisions from brainstorming. Use whenever Brett asks for a master summary, recap, "summarize where we are," "pull this all together," a project status document, or a handoff document for a collaborator or another chat. Trigger on "master summary," "summarize," "recap," "where are we," "document this," or end-of-session consolidation requests.

Master Summary

Heading format (exact)

Begin the heading with the red pushpin: 📌 MASTER SUMMARY — [TOPIC NAME], with the date.

This is the one deliverable type where structure and headings are expected — it's a reference document, not prose. But bullets still carry full sentences with real information, not fragments.

The core discipline: decisions vs. everything else

Separate ruthlessly:

  1. DECIDED — things Brett explicitly approved or directed. Quote or closely paraphrase his direction. Nothing enters this section on inference.
  2. DEVELOPED — work produced and delivered (files, drafts, builds), with what state it's in.
  3. PROPOSED / OPEN — recommendations made but not ruled on, alternatives still live, and open questions, each stated so a yes/no or a choice can answer it.
  4. PARKED / REJECTED — what was considered and set aside, so it doesn't resurface as new.

Never promote a Claude suggestion Brett reacted warmly to into a decision. "Sounds interesting" is not approval.

Status labels (mandatory on every project/asset mentioned)

concept · exploratory · proposed · developing · pilot · active · approved · launched · paused · archived. Never assume a pitch became a partnership, an outline became a book, or a working title became final — working titles are marked (working title).

Relationship labels (when people/orgs appear)

historical relationship · current working relationship · active collaboration · strategic conversation · prospective opportunity. No implied endorsements or partnerships.

Continuity duties

  • Preserve Brett's established terminology exactly (the Sushi List stays the Sushi List; the hub/spokes/rim wheel keeps its names).
  • Connect the summarized work to the existing ecosystem: name which established project each thread belongs to (RBI / FLBD / LifeTogether internal) rather than treating threads as standalone.
  • Flag conflicts with earlier direction openly ("this session's pricing conflicts with the price list built on [date]") rather than silently reconciling.

Numbers and claims

Carry figures exactly as established; where a number was reasoned rather than validated, keep its caveat attached. Never launder an estimate into a fact by summarizing it.

Close with

Next actions — the two or three concrete moves, each with what unblocks it. Not a task dump.
